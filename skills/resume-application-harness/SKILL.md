# 한국형 이력서·자기소개서 작성 하네스

사용자가 잘 정리해서 말하도록 요구하지 않는다. 편하게 말한 내용을 먼저 사실 단위로 나누고, 필요한 부분만 짧게 다시 물은 뒤, 회사 문항과 분량에 맞는 자연스러운 한국어로 정리한다. 기술적인 원장과 검사기는 뒤에서 사용하고 사용자에게 작성 부담을 넘기지 않는다.

## 필요한 참조 문서 읽기

- 인터뷰를 시작하거나 경험을 정리할 때 [conversation-flow.md](references/conversation-flow.md)를 읽는다.
- 경험을 떠올릴 키워드나 후속 질문이 필요할 때 [question-bank.md](references/question-bank.md)를 읽는다.
- 한국어 초안을 쓰거나 고칠 때 [korean-writing-style.md](references/korean-writing-style.md)를 읽는다.
- 특정 회사 문항과 글자 수를 다룰 때 [company-question-routing.md](references/company-question-routing.md)를 읽는다.
- 최종 제출물의 고위험 사실을 감사할 때만 [fact-claim-schema.md](references/fact-claim-schema.md)를 읽는다.
- DOCX·PDF·한영·사진·블라인드 변형을 만들 때만 [output-profiles.md](references/output-profiles.md)를 읽는다.
- 사용자가 영문 이력서 ATS 진단을 원할 때만 [resuml-safety.md](references/resuml-safety.md)를 읽는다. 일반 한국어 자소서에는 `resuml`을 쓰지 않는다.

## 작성 원칙

1. 없는 사건·수치·기간·직책·성과·감정·동기를 만들지 않는다. 글자 수를 채우려고 같은 뜻을 늘이거나 새 사실을 보태지 않는다.
2. 사용자의 거친 말투와 반복은 다듬되 사실의 범위와 강도는 유지한다. `참여`를 `주도`, `사용해 봄`을 `숙련`, 팀 결과를 개인 성과로 키우지 않는다.
3. 사용자가 써 달라고 제시한 문구, 예시, 목표 표현은 그 자체로 경험 사실이 아니다. 그 문구 속 직책·수치·성과·역할을 별도로 확인한다.
4. 사용자가 최근에 바로잡은 사실을 우선한다. 문서와 사용자 설명이 다르면 충돌로 표시하고 필요한 부분만 확인한다.
5. 질문의 답을 먼저 쓴다. 한 문장에는 핵심 하나만 두고, 추상적인 성격보다 실제 행동과 확인 가능한 결과를 보여준다.
6. `STAR`, `CAR` 같은 이름을 사용자에게 강요하지 않는다. 구조화는 내부에서 한다.
7. 질문 은행은 크게 유지하되 한 번에 기본 2~4개, 최대 5개만 묻는다. `없음`, `모름`, `기억 안 남`, `건너뛰기`, `나중에`를 항상 허용한다.
8. 사용자가 길게 말하는 동안 중간에 끊지 않는다. 이미 답한 내용은 다시 묻지 않는다.
9. AI 작성 여부를 판정하지 않는다. 번역투, 상투어, 긴 문장, 반복, 근거 부족만 구체적으로 경고한다.

## 모드 자동 선택

- `빠른`: 한 문항이나 임박한 한 회사 지원. 핵심 6~10개 질문을 2~3회에 나눈다.
- `표준`: 기본 이력서와 재사용할 자기소개 원본. 관련 질문 15~25개를 3~5개씩 나눈다. 별도 요청이 없으면 이 모드다.
- `깊이`: 여러 회사에 반복 지원하거나 경험이 많다. 전체 은행에서 관련 질문 40~60개까지 조건부로 꺼낸다.

사용자에게 모드부터 고르게 하지 않는다. 요청의 범위에서 추론하고, 속도를 바꿔 달라고 할 때만 전환한다.

## 대화 흐름

`목적 확인 → 경험 회상 → 경험 카드 → 위험 사실 확인 → 회사 문항 연결 → 초안 → 분량·문체 검사 → 제출본`

### 1. 목적 확인

다음 중 이미 받은 내용은 다시 묻지 않는다.

- 기본 이력서인지 특정 회사 지원서인지
- 회사·직무·공고·자기소개서 원문
- 최소·최대 분량과 계산 단위: 공백 포함 글자, 공백 제외 글자, byte, 단어
- 기존 이력서·포트폴리오·메모

처음 안내할 때는 다음 취지를 짧게 말한다.

> 문장으로 정리하지 않아도 됩니다. 순서가 뒤죽박죽이어도 괜찮습니다. 기억나는 대로 말하면 경험별로 나누고, 숫자가 확실하지 않으면 모른다고 적어도 됩니다.

회상 키워드는 우선 8~12개만 보여준다. 예: `잘 끝낸 일 / 실수나 사고를 막은 일 / 문제를 고친 일 / 고객을 도운 일 / 동료와 맞춘 일 / 더 빠르거나 정확하게 바꾼 일 / 처음 배워 해낸 일 / 책임지고 마무리한 일`.

### 2. 주저리 답변을 경험 카드로 바꾸기

원문에서 다음을 나눈다: 언제·어디서·공식 역할·맡은 일·문제·본인 행동·판단 이유·다른 사람 행동·도구·제약·결과·근거·이후 바뀐 행동·불확실한 부분.

사용자에게 내부 필드나 ID 입력을 시키지 말고 다음 네 묶음만 보여준다.

- `제가 이해한 사실`
- `아직 확인할 내용`
- `초안에서 빼 둔 추정`
- `이 경험에 붙일 수 있는 키워드와 문항`

경험 카드의 내부 형식과 상태 전이는 [conversation-flow.md](references/conversation-flow.md)를 따른다. 사용자가 일부를 고치면 해당 부분만 수정한다.

### 3. 필요한 부분만 다시 묻기

먼저 결과를 바꾸는 사실을 확인한다.

- 기간·횟수·인원·비율·금액
- 직책·소속·고용형태와 실제 책임 범위
- 혼자 한 일과 팀이 한 일
- 사고·민원·품질·매출·시간 절감 같은 강한 결과
- 기술·도구·외국어의 실제 사용 수준
- 회사 지원 이유처럼 모델이 추론하기 쉬운 내용

숫자가 없으면 만들지 않는다. 마감 준수, 오류 발견, 재작업 방지, 민원 종결, 절차 채택, 재요청, 관리자 확인처럼 설명 가능한 질적 결과를 찾는다. 충분한 카드가 되면 질문을 멈춘다.

### 4. 회사 문항 분석과 경험 배정

문항을 바로 쓰지 말고 먼저 다음을 내부적으로 분해한다.

- 반드시 답해야 할 하위 질문
- 문항 유형과 평가하려는 행동
- 회사·직무·가치 키워드
- 필요한 경험과 근거
- 글자 수의 최소·최대·단위
- 블라인드·민감정보·첨부 규칙

부족한 슬롯만 알려 준다. 예: `관련 경험은 충분하지만 이 회사여야 하는 이유가 아직 없습니다.` 실패 문항은 기대와 실제 결과의 차이와 본인 책임이 확인되지 않으면 `미배정`으로 두고 사건을 만들지 않는다. 한 지원서 안에서는 가능한 한 경험을 겹치지 않는다. 같은 카드를 다시 쓸 때는 서로 다른 확인 사실과 다른 행동·판단을 사용하고, 중복 사실을 사용자에게 알린다.

### 5. 자연스러운 한국어 초안

- 첫 문장에서 질문에 바로 답한다.
- 실제 행동을 1~3개 남기고 배경 설명은 필요한 만큼만 쓴다.
- 결과는 확인된 범위만 쓴다.
- 질문이 요구할 때만 마지막에 직무나 회사와 연결한다.
- `귀사의 발전에 기여`, `역량을 발휘`, `원활한 소통`, `긍정적인 시너지`를 실제 행동 없이 넣지 않는다.
- 사용자가 처음 말한 구체적인 단어, 판단 기준, 사건의 순서를 일부 보존해 개인 말투를 남긴다.

초안마다 긴 해설을 붙이지 않는다. `초안`, `살린 사실`, `확인 필요`, `분량`을 짧게 보여준다.

### 6. 분량과 가독성 검사

초안을 UTF-8 텍스트 파일로 저장한 뒤 다음을 실행한다.

```powershell
node <skill-dir>\scripts\korean_application.mjs count --file <draft.txt> --limit <number> --unit <chars|chars-no-space|utf8-bytes|words>
node <skill-dir>\scripts\korean_application.mjs lint --file <draft.txt> --question-file <question.txt> --limit <number> --unit <unit>
```

회사 계산 규칙이 불분명하면 공백 포함 글자, 공백 제외 글자, UTF-8 byte를 함께 보여주고 최종 입력창에서 다시 확인한다. 검사 경고를 기계적으로 모두 없애지 말고 문맥을 본다.

## 프로젝트 상태

빠른 채팅 수정만 요청한 경우 파일 상태를 강요하지 않는다. 기본본이나 여러 회사 지원서를 만들면 프로젝트 안의 `.resume-harness`를 사용한다.

```text
.resume-harness/
  policy.json
  profile.json
  experience_cards.json
  sources.json
  master_facts.json
  claims.json
  protected_artifacts.json
  applications/<company_role>/
    posting/
    questions.json
    experience_usage.json
    drafts/
    qa/
  sessions/
  runs/<timestamp_slug>/
```

초기화는 기존 파일을 덮어쓰지 않는 경우에만 실행한다.

```powershell
node <skill-dir>\scripts\resume_harness.mjs init --project <project-root> --candidate-id <stable-id>
```

개인정보와 지원 문서는 전역 스킬 폴더에 넣지 않는다. 사용자 이름을 파일명에 강제로 넣지 않고, 기존 또는 사용자가 이름을 바꾼 산출물을 덮어쓰지 않는다.

## 최종 사실 검사와 문서 제작

- 사용 중인 경험 카드의 기간·수치·직책·역할·성과가 모두 확인됐는지 감사한다.
- 불확실한 내용은 제출 문장에서 제외하거나 사용자가 확인할 수 있게 표시한다.
- 사용자가 요청한 경우에만 사실 원장 보고서를 보여준다. 기술 ID를 인터뷰 입력 양식으로 쓰지 않는다.
- DOCX는 `doc` 스킬, PDF 검토는 `pdf` 스킬을 사용한다. 모든 페이지를 렌더링해 잘림·겹침·글꼴·페이지 나눔을 확인한다.
- 사진 포함 한국식 이력서와 블라인드·영문본의 개인정보 규칙을 분리한다.
- `resuml`은 사용자가 영문 ATS 진단을 원할 때만 제한형 도구 세 개를 선택적으로 사용한다. 점수 때문에 키워드·경력·수치를 만들지 않는다.

## 제출 준비 기준

다음이 모두 충족돼야 완료라고 말한다.

- 모든 하위 질문에 답했다.
- 사용한 사건·직책·기간·수치·역할·결과가 사용자 확인 범위 안이다.
- 회사명만 바꾸면 되는 범용 문장이 아니라 해당 문항과 직무에 맞는다.
- 번역투·상투어·반복·긴 문장이 검토됐다.
- 최소·최대 분량과 계산 단위를 확인했다.
- 같은 지원서 안의 경험 중복을 점검했다.
- 생성한 DOCX·PDF가 있다면 텍스트 추출과 시각 검사가 끝났다.
- 기존 파일과 개인정보가 보호됐다.
