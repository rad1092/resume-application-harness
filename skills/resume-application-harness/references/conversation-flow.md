# 대화형 작성 흐름

## 목적

사용자가 무엇을 써야 할지 모르거나 말을 길고 산만하게 해도, 답변을 끊지 않고 사실을 경험 카드로 정리한 뒤 필요한 부분만 다시 묻는다. 질문을 많이 보유하는 것과 한꺼번에 많이 묻는 것을 분리한다.

## 상태 흐름

```text
DISCOVER → CAPTURE → STRUCTURE → CONFIRM → ROUTE → DRAFT → FIT → RELEASE
                ↑          │                    │
                └──────────┴── 부족한 카드만 되돌아감
```

- `DISCOVER`: 기본본 또는 회사별 지원서, 직무, 문항, 제한을 확인한다.
- `CAPTURE`: 회상 키워드를 보여주고 정리되지 않은 답변을 받는다.
- `STRUCTURE`: 원문을 경험 카드로 나눈다.
- `CONFIRM`: 결과에 영향을 주는 사실만 확인한다.
- `ROUTE`: 문항별로 경험을 배정하고 비어 있는 요구를 찾는다.
- `DRAFT`: 질문에 먼저 답하는 한국어 초안을 쓴다.
- `FIT`: 분량, 문항 충족, 중복, 번역투와 가독성을 확인한다.
- `RELEASE`: 최종 문장, 확인 목록, 면접 꼬리질문, 필요 시 문서를 만든다.

다음 상태로 가기 위해 모든 빈칸을 채울 필요는 없다. 지원 문장에 필요한 부분만 충분하면 진행한다. 부족해지면 전체 인터뷰가 아니라 해당 경험 카드로만 돌아간다.

## 모드

| 모드 | 자동 선택 조건 | 질문 범위 | 목표 |
|---|---|---:|---|
| 빠른 | 한 문항, 마감 임박, `그냥 먼저 써줘` | 6~10개를 2~3회 | 현재 사실로 제출 가능한 한 문항 |
| 표준 | 기본 이력서·자소서, 별도 지시 없음 | 15~25개를 3~5개씩 | 재사용 가능한 프로필과 경험 카드 |
| 깊이 | 여러 회사, 경력 다수, 전체 경험 정리 | 관련 질문 40~60개까지 | 경험 라이브러리와 회사별 변형 |

모드를 매번 선언하거나 선택시키지 않는다. 사용자가 질문이 많다고 하면 빠르게, 더 파고들라고 하면 깊게 바꾼다.

## 첫 응답 규칙

이미 받은 공고, 문항, 글자 수, 기존 이력서를 다시 요구하지 않는다. 없는 정보 중 가장 중요한 것만 2~3개 묻는다.

권장 시작 문구:

> 잘 정리해서 답하지 않아도 됩니다. 기억나는 순서대로 적으면 제가 경험별로 나누겠습니다. 숫자가 확실하지 않으면 `모름`, 해당 사항이 없으면 `없음`, 답하기 싫으면 `건너뛰기`라고 써도 됩니다.

처음 필요한 정보:

1. 기본 이력서인지 특정 회사 지원서인지
2. 회사·직무·공고·문항·글자 제한 중 이미 있는 것
3. 가장 먼저 떠오르는 경험 하나

처음 보여줄 회상 키워드 예:

`잘 끝낸 일 / 힘들었지만 버틴 일 / 실수·사고를 막은 일 / 문제를 고친 일 / 고객·동료를 도운 일 / 속도·정확도를 바꾼 일 / 처음 배워 해낸 일 / 갈등을 풀거나 설득한 일 / 책임지고 마친 일 / 칭찬·재요청을 받은 일`

## 질문 배치 규칙

- 한 메시지당 기본 2~4개, 최대 5개 질문만 보낸다.
- 질문 앞에 선택 가능한 회상 키워드를 짧게 붙인다.
- 사용자가 한 줄만 답하면 관련 키워드를 더 보여준다.
- 사용자가 길게 답하면 질문을 더 쌓지 말고 바로 구조화한다.
- 같은 사실을 다른 표현으로 다시 묻지 않는다.
- `모름`, `기억 안 남`, `없음`, `건너뛰기`, `나중에`를 답으로 인정하고 해당 질문을 닫는다.
- 민감한 가족사, 질병, 정치·종교, 출신지, 사적인 공백 사유는 선택 질문으로만 다룬다.
- 사용자가 `그냥 써줘`라고 하면 확인된 사실만으로 초안을 먼저 만들고 중요한 미확정 항목만 표시한다.

## 주저리 답변 분해

원문을 문장 품질로 평가하지 않는다. 다음 사실 조각을 찾는다.

1. 시기와 기간
2. 장소·조직·경험 유형
3. 공식 직책과 실제 맡은 일
4. 평소 업무와 특정 사건
5. 목표·문제·제약
6. 본인이 직접 관찰하거나 판단한 것
7. 본인이 직접 한 행동
8. 팀원·상사·고객 등 다른 사람이 한 행동
9. 사용한 도구·자료·장비·절차
10. 결과와 확인 방법
11. 실패·실수·위험과 수습
12. 이후 바뀐 행동
13. 불확실하거나 서로 충돌하는 내용

반복되는 주변 이야기는 버리지 말고 `raw_answer_refs`에 남긴다. 초안에는 핵심 사실만 쓴다.

## 경험 카드

내부 저장 예:

```json
{
  "card_id": "EXP-001",
  "status": "draft",
  "working_title": "납품 일정과 안전을 함께 관리한 경험",
  "period": {"value": null, "confidence": "unknown"},
  "setting": "",
  "experience_type": "employment",
  "official_role": "",
  "personal_role": "",
  "goal_or_problem": "",
  "actions": [],
  "decision_and_reason": [],
  "people_involved": [],
  "tools": [],
  "constraints": [],
  "results": [],
  "evidence": [],
  "learning": "",
  "reusable_behavior": "",
  "competency_keywords": [],
  "job_keywords": [],
  "fact_confidence": "mixed",
  "uncertain_points": [],
  "prohibited_extensions": [],
  "blind_recruitment_risks": [],
  "raw_answer_refs": []
}
```

상태:

- `draft`: 원문에서 추출했지만 확인이 남아 있다.
- `user-confirmed`: 사용자가 요약이 맞다고 확인했다.
- `source-verified`: 원문 문서나 기록으로도 확인했다.
- `restricted`: 민감하거나 특정 출력에서 쓰면 안 된다.
- `retired`: 사용자가 틀렸다고 바로잡아 더 이상 쓰지 않는다.

사용자에게 이 JSON을 입력시키지 않는다. 구조화 뒤에는 다음 형식만 보여준다.

```text
제가 이해한 사실
- ...

아직 확인할 내용
- ...

초안에서 빼 둔 추정
- ...

쓸 수 있는 키워드·문항
- ...
```

## 위험도 기반 확인

### 반드시 확인

- 기간, 날짜, 횟수, 인원, 금액, 비율, 처리량
- 공식 직책, 고용형태, 사람 관리 여부
- 본인 행동과 팀 행동의 구분
- `사고 없음`, `민원 감소`, `품질 향상`, `매출 증가`, `시간 절감` 같은 강한 결과
- 자격, 교육 이수, 도구·기술·외국어 수준
- 모델이 사용자의 동기를 추론한 문장

### 바로 다듬어도 됨

- 중복 삭제
- 어순 수정
- 긴 문장 분리
- 구어를 문어로 바꾸기
- 상투어를 제거하되 새 사실을 넣지 않는 수정

### 사실 상태

- `확인됨`: 사용자 또는 자료가 명시했다.
- `표현만 정리 가능`: 사실은 분명하고 문장만 거칠다.
- `의미 확인 필요`: `많이`, `좋아졌다`, `관리했다`처럼 범위가 모호하다.
- `추정 금지`: 숫자·기간·직책·성과·감정을 모델이 채워야 한다.
- `민감정보`: 문항과 무관하면 제외하고 블라인드 규칙을 확인한다.

## 충분한 경험의 기준

다음 중 핵심 다섯 가지가 있으면 초안을 시작한다.

- 어떤 상황이었는지
- 본인이 맡은 일이 무엇인지
- 본인이 실제로 한 행동이 무엇인지
- 왜 그렇게 했는지 또는 어떤 기준을 지켰는지
- 확인 가능한 결과 또는 이후 달라진 행동

숫자나 화려한 성과는 필수가 아니다. 사용자가 설명할 수 있는 행동과 결과가 중요하다.

## 문항 라우팅 전 사용자 안내

먼저 문항을 짧게 해석한다.

> 이 문항은 `지원 이유 + 관련 경험 + 입사 후 활용` 세 가지를 묻습니다. 현재 카드로 관련 경험은 충분하지만, 이 회사를 고른 구체적인 이유가 없습니다. 공고에서 실제로 마음에 든 업무나 조건을 편하게 말해 주세요.

문항을 해석했다는 이유로 모든 슬롯을 질문하지 않는다. 기존 카드에 없는 필수 슬롯만 묻는다.

## 경험 사용표

한 지원서에서는 다음 표를 내부적으로 유지한다.

```text
문항 1 지원동기       EXP-003
문항 2 직무역량       EXP-001
문항 3 협업           EXP-004
문항 4 실패와 학습    미배정
```

- 기본적으로 같은 경험을 여러 문항에 반복하지 않는다.
- 적합한 경험이 하나뿐이면 약한 이야기를 억지로 만들지 않는다.
- 재사용할 때는 서로 다른 확인 사실과 행동·판단을 쓰고, 같은 사건을 다시 쓴다는 점을 사용자에게 알린다. 이 세 조건을 충족하지 못하면 미배정으로 둔다.
- 회사가 달라지면 경험은 재사용할 수 있지만 회사명만 바꾼 문장은 만들지 않는다.

## 초안 확인 형식

```text
초안
...

살린 사실
- ...

사실 확인 필요 2개
- “배송 순서를 직접 조정했다”가 맞나요?
- “해당 근무 기간에 업무 중 운전 사고가 없었다”로 한정하면 맞나요?

분량
- 공백 포함 684/700자
- 공백 제외 521자
- UTF-8 1,742 bytes
```

간단한 문체 수정에는 매 문장 승인을 요구하지 않는다. 위험 사실이 모두 확인되면 `user-confirmed`로 바꾸고 최종본을 만든다.

## 산출물 순서

사용자에게 기술 파일보다 다음 결과를 먼저 준다.

1. 재사용 가능한 경험 정리본
2. 기본 한국어 이력서
3. 지원동기 없는 기본 자기소개 원본
4. 회사별 문항 분석과 답변
5. 사실 확인 필요 목록
6. 최종 답변에 기반한 면접 꼬리질문
7. 요청 시 DOCX·PDF·영문본·ATS 진단

## 하지 말아야 할 것

- 첫 응답에 질문 20~30개를 나열한다.
- 산만한 답을 읽자마자 상투적인 완성문으로 덮어쓴다.
- 사용자가 모른다고 한 수치를 추정한다.
- 증빙 원장 입력부터 요구한다.
- `참여`를 `주도`, 직급을 인력관리 경험으로 확대한다.
- 실패를 억지 성공담으로 만든다.
- 한 경험을 모든 문항에 반복한다.
- 글자 수가 부족하다고 같은 뜻이나 회사 칭찬을 반복한다.
- byte 제한을 글자 수로 처리한다.
- 민감한 공백 사유를 자세히 설명하도록 강요한다.
